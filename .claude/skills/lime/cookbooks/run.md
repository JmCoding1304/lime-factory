# run — build / add / fix a well-scoped thing

1. **Write the ticket** as `.lime/tickets/<NN>-<slug>.md`, `NN` = `lime ticket next` (never counted from the folder — it is empty after delete-on-close) (not a plan — the Spine's planner writes that): `Workflow: feature|bug-fix` header, `Status: open`, `Blocked by:`/`Spec:` if any, then the four-line prompt:
   - `## Ask` — what, in the user's words, tightened.
   - `## Where` — from one `lime scout "<ask>"` (≤20 lines, printed inline). Don't read the target source yourself. One backticked path per line, with symbols/prose after it (`` `lime/cli.py` — the run command ``); the launch overlap check reads each line's first backtick token as the path.
   - `## Done means` — the observable finish line.
   - `## Out of scope` — what this ticket is not.
   - Ticket-cutting rule (independent of SKILL.md): a ticket adding a job, poll, upload, external call, or a writer of rows another module owns spends one of its six `Done means` bullets on the failure or re-run case. This is never `Out of scope`, and naming a follow-up ticket does not make omitting it safe. Keep the six-bullet ceiling: split rather than add a seventh.
   - Every `Out of scope` entry carries a ticket number or the literal word `never`.
   - An ownership ticket ships with a guard named in `Done means`: an import guard **plus one behavioural test**. `Where:` lists every existing writer the scout identified. An ownership ticket never runs in the same batch as a ticket writing those rows; serialize with `Blocked by:`, never an overlap override.
   - After every scaffold ticket, cut a shell-defaults ticket for that layer. Web checklist: query defaults, auth caching, error boundary, not-found, nav, chunking. Backend: settings that fail closed.
   - Behaviour keyed on values another package emits is parametrized over the emitted corpus plus invalid and unknown values, never synthetic strings in place of that corpus.
   - Tests import the production config factories; any test-only override is explicit and itself tested.
   - An ADR is an Architecture Decision Record: it records a decision with its context and consequences. ADRs merge `proposed`; the owner accepts them in the slice's owner QA `Type: task` ticket, never at merge. A Consequences sentence reading `stays open`, `halts`, or `runs inline` is a **review flag**, not an accepted default or a ban on those words.
   Save it as a file only — don't commit it: `lime run` commits it on the Run's branch, and a ticket committed on main can never fast-forward at deploy (ticket 59).
2. **Ratify** — read it back to the user, one key to confirm. Check it against SKILL.md's ticket-cutting rule: the resolved builder limits (selected profile's clock, token and added-lines ceilings), tests and docs counting toward the cap, headroom, runnable checks, and a `Blocked by:` split instead of a stretched or exempted ticket. This is the only ask; nothing else in the Run stops for a human.
3. **Launch** — `lime run NN [NN…] [--profile X] [--deploy]` through your shell tool (backgrounded or blocking, per SKILL.md), never a subagent. A ratified cut launches as one `lime run <every ticket of the cut> --deploy` — all its `Workflow:` tickets in one command, never link by link; `Blocked by:` is the queue. The owner QA `Type: task` ticket stays out — it is the owner's, never a Run (a Where-less ticket refuses the whole batch at preflight). Before reserving anything, `lime run` compares the ticket's Where paths against unmerged Runs from two sources: published `origin/lime/**` Run branches, and this project's own started, unmerged, unremoved Runs read from `.lime/runs/lime.db`. A local holder is named by Run id (`Run <run_id> (<branch>)`); a remote-only one keeps its branch key. An exact path or a directory-prefix conflict names each holder and path and exits 2 — wait for it to merge or to be removed (`lime runs rm <run_id>` discards that Run's work), or deliberately re-launch that one fresh ticket with `--allow-overlap` (a single fresh ticket only; rejected for a batch or `--resume`). A holder the ticket explicitly names under `Blocked by:` is exempt from this overlap check only — `Blocked by:` refusal itself is unchanged. A stopped red Run keeps holding its paths until its branch is merged or the Run is removed; a live Run holds even when its carried ticket already existed at birth. No origin does not skip this check — local Runs are still inspected; only remote merge inference is skipped. Then `lime run` reserves the number on origin (`refs/lime/tickets/<NN>`); a number another Run already holds is refused — renumber with `lime ticket next`. Two more refusals sit with this reservation: `lime run` refuses Where overlap (`--allow-overlap` overrides that one refusal, retaining its existing single-fresh-ticket restriction), and the plan gate refuses a step missing `failure:` or `writers:`. The override never bypasses reservation, dependencies, or the plan gate. A multi-ticket batch is one process: port-capped concurrency, the next unblocked, non-overlapping ticket starts when one exits; a candidate overlapping a sibling this batch already spawned is held in `pending` even before that sibling records its trace row; when nothing can run it ends with `held: overlap with …` (or `still blocked`) and a nonzero exit. `--deploy` (fresh tickets only — never with `--resume` or `--allow-overlap`) carries each child that ends success through `lime deploy`'s unchanged gates and then launches what it unblocks; it needs `auto_deploy: staging` or `prod` in `.lime/config.yaml` (the template stamps `off`; off or missing refuses before anything launches), prints that target at launch, and ends with one report headed by it — deployed · failed (with its resume command) · held (with its blocker). A link refused only because CI is pending on the docs merge `lime deploy` pushed waits once more for that CI (same ceiling, outside the launch lock) and deploys again; any other refusal holds its dependents. A non-empty `deploy:` stops at each link. It runs for hours: background it, never a foreground shell with a timeout. A ticket whose `Blocked by:` file still exists is refused — check first if that's a surprise. Every Run pins its birth HEAD (`runs.base_sha`) at launch; every diff, accounting and PR stat is measured against that immutable pin, never a moving default branch (the default branch is only the PR target).
4. **Monitor, don't poll** — wait for the exit notification (never a sleep-loop), then `lime trace <run-id> --summary` for the report: phases, gates, cost, last event. A `lime run` batch (never a single ticket, never a retry) starts one watchdog beside itself in its own session; when the batch process ends by any means — exit, crash, `kill -9` — the watchdog claims the batch once if its `processes` row is still open and launches one retry that launches the still-`queued` children, waits for and deploys a still-running one, deploys one that passed unwatched, resumes once one killed with the batch, and leaves one that failed on its own with its resume command; dropped children stay dropped and no ticket gets a second Run. That claim is one-shot — two watchdogs racing start exactly one retry — and a retry starts no watchdog of its own, so a retry that dies is never retried. An intentional stop — Ctrl-C or `kill` (SIGINT/SIGTERM) — closes the row first, so the watchdog exits without retrying. A retry that fails to launch stays claimed: nothing tries again, and the claim, the failure reason and the retry's exit are appended to `.lime/runs/watchdog-<batch-id>.log`.
5. **Red Run** — never resume blind, never report-and-stop. A batch that died is retried once by its watchdog, so check `lime status` before relaunching or resuming any of its tickets by hand. `lime trace <run-id>` for the failing phase's error, then:
   - **Role work wrong / ticket changed** (plan, verify exhausted, review — any edit to the ticket's Ask/Where/Done means/Out of scope, or a changed resolved builder limit) → edit the ticket (or config), then re-plan explicitly: `lime run --resume <run-id> --replan`. An ordinary `--resume` refuses a cached plan whose ticket, planning inputs/limits or `plan.md` changed; `--replan` records the decision, invalidates scout and re-plans against the current ticket while preserving the existing work.
   - **Review stuck, code done** (every phase succeeded, the reviewer kept blocking on evidence, ticket and plan unchanged) → `lime run --resume <run-id> --rereview`: records the decision, invalidates from the last verify before the first review and clears the agent map; scout, plan and builds replay (earlier verifies as recorded), verify re-measures the current tree and a fresh review/revise cycle runs with the full revise budget. Refused without `--resume`, with `--replan`, on a Run that never reached review or already committed its code, and on a changed ticket/plan (that is `--replan`).
   - **Test timeout** (the stop's first line says the test command `ran out of time` and names `commands.test_timeout`; not the plan's fault, so never `--replan`) → the one protected-file edit that is yours: in the project's `.lime/config.yaml` change only `commands.test_timeout`, to the value the stop's last line names — no other key, no other protected file. Leave it uncommitted; never commit or push it. Tell the owner the old and new value, then run `lime run --resume <run-id>` (lime re-reads the config on resume and re-runs that verify). When the stop names no value (the Run already stopped once on a test timeout), raise nothing and hand the Run to the owner.
   - **Mechanics** (git, push, gh, setup, ports) — the ticket and plan are unchanged → fix it yourself, `--resume`.
   - **Invalid pinned base** — the error says `branch rebased/merged past its base — start a fresh Run` and names the offending `base_sha`: the Run's immutable birth identity no longer resolves to an ancestor of HEAD (the branch was rebased or merged past it). Preserve and report the existing work, then start a fresh Run for it. Do not mechanically `--resume`/`--replan`, try a rebase repair, or reset/backfill the pin — the pin is never re-derived and old work is never backfilled onto it.
   - **Unclear** → give the engineer the error verbatim and ask.
6. **Delete-on-close** — the ticket dies with the Run's docs commit; merging the PR closes it. Nothing to do here.
