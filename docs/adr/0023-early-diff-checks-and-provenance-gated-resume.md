# Early diff checks and provenance-gated resume evidence

Status: items 2 and 3 superseded by [ADR 0060](0060-diff-size-is-measured-never-a-stop.md) (the early check and the 80% advisory); item 1 stands, and item 4 is superseded by [ADR 0057](0057-resume-reruns-only-the-latest-verify.md).

[ADR 0019](0019-measured-diff-cap-overflow-stops-the-chain.md) made a measured overflow stop the Chain and preserve the Run; [ADR 0021](0021-event-bound-recovery-of-a-preserved-overflow.md) added the engineer-approved recovery, and closed by leaving "early checks, verification-cache invalidation" explicitly out of scope. That is what this ADR builds. Two holes remained. First, the cap was only measured at the end of a step's verify, so a step that overran cumulatively was discovered late — after the quality commands had already run and the next step was about to start. Second, resume replayed any earlier succeeded phase by name: a cached verify could be reused after its code, base or accounting policy had changed, and a cached plan could be reused after the ticket was edited underneath it. The failure mode is a Run that reports success against evidence that no longer describes what was built.

1. **One accounting implementation, shared.** `diff_accounting.evaluate()` resolves the effective policy (exclude, uncounted, cap, `ACCOUNTING_VERSION`), the base/HEAD identity, per-file stats and exemptions into one read-only `AccountingMeasurement`. The early check and the final verify both call it, so neither sums stats nor formats overflow on its own and the two can never disagree. It never stages, writes the index/HEAD/worktree or dumps file contents; a git inspection failure is returned as data (an ordinary failure), never raised and never a fabricated overflow.

2. **Cumulative growth is measured between build steps.** After each build and each revise, and before any quality command runs, `feature.run` takes a fresh early measurement. A measured overflow stops the Chain immediately through the existing `_stop_for_diff_cap_overflow` handler, so the worktree, ticket, plan and required content are preserved exactly as ADR 0019 promises. The early check opens no full verify phase and records no `VerifyOutput` envelope — it publishes a `diff_early_check` trace event and a console note — so it can never masquerade as a completed full verify.

3. **The advisory is a warning, not a reduced cap.** At or above 80% of the effective cap and at or below it, the measurement carries an advisory line (`5 * counted >= 4 * cap`, integer-only). It is reported to the next builder's prompt and to the console, and it never fails the Run and never lowers the cap. Overflow stays a strict `>`; equality at the cap passes.

4. **Cached verification is reused only on matching provenance.** A verify records `VerificationProvenance`: a read-only content fingerprint (tracked committed content, index state, working-tree content and non-ignored untracked paths and content — including uncounted generated files, NUL-safe and byte-digested), the HEAD, base-tip and merge-base SHAs, the effective accounting policy and the configured quality command set. `verify` replays a cached pass only when all of them still match; otherwise it records a cache miss, invalidates the stale verify and its dependent successes, and runs a fresh full quality-plus-accounting pass. Missing, legacy or malformed evidence fails closed — a pass with no provenance is never reusable. Legacy envelopes without the fields replay unchanged.
   *Superseded by [ADR 0057](0057-resume-reruns-only-the-latest-verify.md) item 2: the fingerprint and provenance check are removed, and on resume only the latest verify re-runs.*

5. **An edited ticket cannot silently continue under the old plan.** A plan records `PlanProvenance` (ticket `sha256`, the exact planner prompt, the produced `plan.md` `sha256`). An ordinary `lime run --resume` refuses a replay-eligible plan whose ticket or `plan.md` changed, or whose provenance is missing or legacy, before any status, phase, session or worktree mutation. The explicit decision is `lime run --resume RUN_ID --replan`: it records a `replan_decision` event, invalidates scout (and everything after it, falling back to plan), clears the stale runtime session mapping and re-plans against the current ticket, preserving the existing work. `--replan` requires `--resume` and is refused alongside `--rescope-event`/`--recovery-decision`, whose recovery already re-plans. `latest_envelope` ignores invalidated phases, so a stale verify or review cannot be fed to a downstream consumer.

We considered,

- **Measure only at the final verify.** Rejected: an overrun is discovered after the quality commands have run and the next step is queued, so work that can never fit is built anyway.
- **A reduced hard limit at 80%.** Rejected: the engineer asked for an advisory; a second, lower cap would silently stop Runs the agreed cap permits.
- **Reuse a verify by name, as before.** Rejected: a pass measured against different code, base or policy is not evidence about the current tree; reuse without provenance is the stale-evidence hole this closes.
- **Auto-replan when the ticket changes.** Rejected: an edited ticket is an engineer decision about what the work is, so the Run refuses and asks for `--replan` rather than silently planning against a ticket nobody reconsidered.
- **Let the early check record its own verify envelope.** Rejected: it would let an unverified measurement stand as a completed full verify in the trace and in downstream handoffs.

Trade-offs accepted: every build and revise now pays an extra read-only git measurement, and a resumed Run whose code, base or policy changed loses its cached verify and re-runs the full quality set rather than reusing a stale pass — the cost of never reporting success against evidence that no longer matches. A ticket edit now costs an explicit `--replan` instead of a plain `--resume`. The resume-evidence regression matrix, budget-aware ticket cutting and planner guidance remain out of scope.
