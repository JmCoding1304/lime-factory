# Resolved builder limits are one prompt line and part of plan identity

The planner was told only "~150k tokens" and the builder was told nothing, so a plan packed implementation, a big test matrix and unobtainable evidence (logged-in browser checks, post-push CI) into one step that died at the 1800 s ceiling or on a blocker the plan never named. Nothing in the Spine compared what a plan assumed against the numbers that would actually enforce it. [ADR 0023](0023-early-diff-checks-and-provenance-gated-resume.md) gated plan replay on the ticket and `plan.md` bytes and explicitly left "budget-aware ticket cutting and planner guidance" out of scope; this completes it.

1. **One deterministic limits line, rendered once.** `limits.line()` resolves the *builder's* Session `timeout_s`, the effective token warn/stop (agent override beats run, capped by the model window) and the Run's cumulative `max_added_lines` plus the uncounted patterns, through `agents._context_window`, `budget.thresholds` and `config.resolve_commit_settings` — it duplicates none of those algorithms and `agents` never imports it, so there is no cycle. `limits.append()` adds exactly one such line to a raw planning or build input. The line carries no elapsed time, remaining lines, live usage or git statistics: those are dynamic and would make equivalent configurations render differently, so they are excluded by design.

2. **Planner and builder see the same numbers.** `phases.plan` augments the raw request with the line before replay, the planner call and provenance; `feature._build_prompt` and `phases.revise` append the same line to every builder call, kept apart from the dynamic fresh-session git facts and measured advisory feedback. The planner's own timeout never leaks in — only the builder's resolved limits do.

3. **A resolved-limit change is a new plan identity.** `PlanProvenance` (bumped to version 2) stores the exact augmented prompt, so the recorded identity now spans the ticket/bug-fix input *and* the resolved-limit line. An ordinary `lime run --resume` recomputes that prompt read-only and offline from the run's stored profile — never the default — and refuses a plan whose limits changed exactly as it refuses an edited ticket. The refusal precedes any status, phase, session or worktree mutation; `--replan` remains the explicit decision. Unchanged limits keep a multi-step resume's replay intact: completed builds play, only the unfinished step re-runs.

4. **A stale plan drops its dependents.** On a cache miss `phases.plan` invalidates the cached plan and everything downstream of it (including cached `build_N` rows) and clears the stale runtime session map, so an old plan cannot execute from replay nor continue in a stale builder session. Live token usage recorded against the plan phase never changes plan identity — only resolved limits, the prompt and the plan bytes do.

5. **The planner refuses what cannot run.** The planner prompt sizes each step against these limits and aims at or below ~80% of each ceiling; estimates stay advice, never a numerical fail gate. Every required check in a step names the owning phase and the executable command or concrete setup that makes it runnable; a test or tool the ticket itself creates is valid when the plan assigns its creation. A prerequisite needing host packages, external auth, live data or pre-push CI that cannot be satisfied locally makes the planner `fail` with a concrete setup or a `Blocked by:` split proposal before any builder work. Explicitly ratified downstream/post-push CI stays downstream and is not a local build/verify prerequisite.

We considered,

- **State the limits in a prompt template.** Rejected: a hardcoded number drifts from the resolved config; resolving the real values keeps the planner and builder sized against what will enforce them.
- **Include live usage and elapsed time in the line.** Rejected: they are dynamic, so identical configurations would render differently and every resume would look like a limit change.
- **Compare only the ticket bytes on resume, as before.** Rejected: raising the cap or dropping the time ceiling under a cached plan would silently continue a plan sized for limits that no longer apply.
- **Auto-replan when the limits change.** Rejected: limits move for reasons unrelated to what the work is, so the Run refuses and asks for `--replan` rather than silently re-planning.
- **Fail the plan on an oversized estimate.** Rejected: estimates are advice; a numerical gate would stop Runs the agreed caps permit. The refusal is reserved for a check that genuinely cannot run.

Trade-offs accepted: raising a profile timeout, a budget threshold or `commit.max_added_lines` — or editing the uncounted list — now costs an explicit `--replan` on the next resume of an affected Run, the price of never building against stale limits. The planner prompt and the ticket-cutting skill text become behavior-bearing Markdown the builder owns. Caps, exemptions, thresholds, `timeout_s` defaults, models and the `.lime/trust.yaml` fence are unchanged; line-count estimation stays advisory.
