# Retry transient pi stream errors in place instead of failing the Run

Two same-day dash-lean Runs (278e4fd2, a1270ab7) died mid-phase on provider-side stream failures the model had no way to avoid — a dropped SSE connection and a generic AbortError — neither of which matched any of pi-ai's own retryable patterns. `agents.py` raised on `status != "ok"`, `Run.phase()` treated the raise as a phase failure, and `close_run(ok=False)` ended the whole Run: 44 builder turns and a completed reviewer `review.md` were both orphaned. Worse, `agent_map.json` was only written on the success path, so `--resume` had no session_id to rejoin even the on-disk `runtime_sessions/` state.

We considered two responses and chose one:

1. **Leave it to `--resume`** — a human re-runs the Run and lime resumes the last agent map entry. Rejected: the agent map entry did not exist for the failed phase (write was success-only), so resume had nothing to rejoin; fixing only that would still burn a full Run-restart cycle for a transient network blip.
2. **Retry the phase in place, bounded, before the Run fails** — classify `status='error'` results by a denylist regex (`NON_TRANSIENT_ERROR`): anything that doesn't look like an auth/quota/context/bad-request problem is treated as transient and gets `STREAM_RETRIES` (2) same-session re-sends with doubling backoff, prompting pi to continue from where it stopped. `agent_map.json` is now written before the first send (`_remember_session`), carrying the session_id and the phase's own `runtime_sessions/` dir, so even an exhausted-retry failure leaves `--resume` a real session to rejoin. We built this.

The trade-off in (2) is a heuristic classifier standing in for the real one: pi-ai's actual retryable-pattern list (`pi-ai/dist/utils/retry.js`) is out of scope by ticket 76's own boundary, so lime cannot ask pi "was this transient" — it can only guess from the error string via `NON_TRANSIENT_ERROR`. A wrong guess in either direction costs something: treating a real auth failure as transient wastes two retries and ~15s before failing anyway; treating a genuinely transient message as non-transient (if it ever matches the denylist by accident) fails fast exactly like today, so the floor is no worse than pre-fix. We accepted an allowlist-of-badness over an allowlist-of-goodness because the failure modes seen in production (`terminated`, injected SSE JSON, AbortError, idle timeout) are an open, provider-specific set that would otherwise require enumerating every transient wording ourselves; the denylist only needs to name the few things that mean "this is not the network's fault."
