# A pi Session ends on its first accepted submit

pi ends a turn only when every tool result in the batch is terminating. A model can call `write` and `submit` in one assistant message, and the `write` result carries no terminate flag, so the turn goes on — and with `tool_choice: required` (the scout default) the next turn must call a tool, so the model repeats `write` + `submit`, then repeats it again until the wall-clock ceiling. In acmeweb Run `a3805f35`, two scout phases produced 124 "Report accepted" replies this way; the ceiling then discarded the accepted Envelope and failed the phase as "no envelope", and the resume reattached to the same unclosed Session and looped again. ADR 0011's nudge assumes the model stops when asked; here it had already delivered the report and kept working because the turn never closed.

1. **The first accepted `submit` wins and stops the pi process at that transition.** The `_Stream` latches `envelope` on the first non-error `submit` result and never replaces it; an empty dict is still a dict (a `is not None` test, never truthiness). The moment the envelope appears in the read loop, `agent_pi` cancels the timer and runs one bounded signal ladder — before `agent_settled`, EOF, another assistant answer or the timer. A schema-rejected `submit` is not acceptance: it records `submit_error` and the model may call `submit` again. An accepted envelope also wins the adapter's terminal status: a non-zero or signalled child exit reports `ok` with that envelope, never a stale timeout or "no envelope".

2. **An accepted Envelope is delivery even when the ceiling fires.** If the timer fires before acceptance, or is already in flight when acceptance cancels it, the accepted report survives: the adapter returns `ok`, `_send_once` normalizes a pi `timeout`-with-envelope to `ok`, and `_timeout_kill` asserts it only ever receives a result with no envelope. A phase whose submit was accepted never fails as "no envelope".

3. **Acceptance closes the pi Session, so a resume starts fresh.** The stream emits a once-only `submit_accepted` notification; the orchestrator closes the matching Session in the agent map — in memory and on disk — before parsing, gates or permissions can throw, and a delivered result envelope closes it too (idempotently). A later parse or gate correction therefore opens a NEW Session (`accepted_session_reopen`), carrying the original task, the accepted report and the correction, and spending neither the `stream_fresh` allowance (ADR 0009) nor the Continuation allowance (ADR 0011). A stale notification bound to a Session that is no longer current never closes its replacement. `_runtime_session` reads the closed flag and starts a fresh Session on resume.

We considered,

- **Refuse `submit` when it is batched with other tools.** Rejected: the batch is the model's right call, and a `submit` guard would turn a valid delivery into a denial; the fix belongs to the Spine's lifecycle, not the tool.
- **Change `tool_choice: required`.** Rejected: it is the scout's deliberate default, and the loop is a symptom of the turn not closing, not of the tool choice.
- **Keep last-accepted-wins (ADR 0007) and let the ceiling keep the report.** Rejected: the last submit is exactly the repeated one the loop produces, and the ceiling path is the one that threw the correct report away.

Trade-offs accepted: the pi envelope contract changes from last-accepted to first-accepted, so ADR 0007's "last accepted `submit`" wording is superseded on that point while its text-vs-tool decision stands; an accepted submit now spends a Session even when a gate later rejects the report, so a correction costs a fresh Session rather than reusing the closed one; and a timeout that already holds the report is reported as `ok` rather than `timeout`, losing the wall-clock fact from the status line (it remains a measured timeout for partial classification via `timed_out_with_envelope`). The Claude Code adapter's statuses are untouched (171).
