# Ticket carried into the worktree, never committed on the default branch

A ticket file must stay untracked on the engineer's default branch — `lime run` carries it into the Run's worktree and commits it there as the branch's first commit. We rejected the old contract (committed on `main` before a Run) because of a deploy collision that made it unrecoverable:

1. **Committed on main** — the first three tickets had the engineer `git add` + `git commit` the ticket file on `main` before every Run. This meant local `main` always had at least one commit ahead of `origin/main`. When the Run's PR merged via `gh pr merge --merge` (which creates a merge commit on the remote), `origin/main` advanced past local `main` via a path local `main` could not fast-forward through. Every deploy failed `--ff-only`, and the manual workaround (rebase) made it worse by rewriting the pending commit hashes so they never matched what GitHub later merged.
2. **Carried into the worktree** — the Run now branches off `origin/<default>` (fetched), not local `<default>`, copies the ticket file into the worktree, and commits it there as `ticket: <slug>`. Local `<default>` stays at the same commit as `origin/<default>` throughout the Run, so `lime deploy`'s `--ff-only` always succeeds. The ticket file remains untracked on the local default branch until the PR merges; `lime deploy` cleans up the leftover copy after a successful fast-forward.

The trade-off is between file-ownership hygiene (an untracked ticket file on the default branch while the Run is open) and deploy reliability (a guaranteed fast-forward instead of a silent divergence that only surfaces at deploy time). We accepted the untracked-file cost because the engineer's habit of writing a file and leaving it on disk is the same either way — only the `git add` step was dropped — and the benefit is a deploy that never asks the engineer to rebase.
