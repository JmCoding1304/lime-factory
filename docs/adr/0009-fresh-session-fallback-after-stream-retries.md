# Fresh-session fallback after in-place stream retries are exhausted

In-place same-session retries of transient pi stream errors (ADR 0008) saved most dash-lean Runs, but three real Runs still lost five phases: the in-place backoffs (5s, 10s) were too close to pi-ai's own retry timer (~2s), and once `STREAM_RETRIES` is exhausted the phase dies anyway — every one of those five phases succeeded on a human `--resume` with a fresh session. We added a second retry layer before the phase fails.

We considered three options and chose one:

1. **More in-place retries only** — raise `STREAM_RETRIES` from 2 to 4. Rejected: the stream error is caused by provider-side state (SSE dropout, idle timeout, goroutine death) that persists inside the same session. Re-sending the same prompt to the same session is at the mercy of the same downstream state. Even if one more try sometimes helps, the ceiling is still bounded by that state, not by retry count.
2. **Infinite loop until ok** — retry in-place forever. Rejected: a genuinely broken session would cycle until the Budget killed it, which is the same cost as a fresh session but slower (smart-zone warn/stop takes minutes) and trashes the trace with noise.
3. **Lengthen in-place backoffs then fall back to a fresh session** — fixed: backoffs to 15s/30s so pi's own retry fires and settles before lime's first re-send. New: when in-place retries are exhausted and the transient condition persists, spend the Phase's one §9 continuation on a brand-new session with the original prompt — same mechanism already used for Budget-kill continuation, now also triggered by `status=error`/`timeout` with a transient error text. The fresh session carries none of the old session's corrupt context; the original prompt is its first turn. If the fresh session also fails, the phase fails with a combined error message naming both layers.

We accepted the trade-off of sharing the §9 continuation between Budget kills and stream errors: a phase that hits a stream error AND a Budget kill in the same phase now fails at the second event instead of getting a second fresh session. In practice the fresh-session retry succeeds 4/4 in observed runs, so this conflict has never triggered and the Budget ceiling on a clean fresh session (no corrupted context) is almost never hit. If it becomes a problem, ticket 81 is already in the queue to raise the 30-minute per-send cap.

**Update (run 95192c3a): independent allowances superseding shared-continuation trade-off.** The shared-allowance design above caused timeout → partial → Continuation then three stream failures in the Continuation session, with no further recovery path. Stream errors now consume a dedicated `stream_fresh` allowance independent of the `continuation` (partial-envelope) allowance. A Phase therefore supports at most three sessions: two replacements (one stream-fresh, one partial-envelope Continuation) in either order. Session ordinal (`session_index`) advances monotonically and independently of the DB `continuation` counter, so directory names (`01-builder`, `.1`, `.2`) are stable regardless of which allowance was spent first. The stream-fresh recovery prompt preserves the interrupted session's opening text, any in-flight correction, and the canonical handoff note. The direct `_send_once` fallback (no recursive `send()`, no second retry loop) matches the original bounded-retry bounds. A second exhausted outage fails the phase without another fresh send.
