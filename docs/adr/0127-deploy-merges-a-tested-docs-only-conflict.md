# Deploy merges a tested docs-only conflict — the one exception to ADR 0029 §2

Status: accepted

Ticket 274 gave the documenter a docs resolver so two Runs that both add glossary lines to `CONTEXT.md` stop colliding. ADR 0029 §2 then stood in the way: it builds the merged tree in a throwaway detached worktree, writes only that throwaway path, and leaves the Run's checkout, the default checkout and every ref untouched — no merge into the Run branch, no checkout switch, no merge commit. That rule is right for code, where a conflict means two writers changed the same behaviour and only a person can choose. But a docs conflict that resolves to both sides' additions is a tree `lime deploy` can build and test, and under §2 as written there is nowhere to record the resolution: the gate tests the merged tree, then refuses, because it may not move the PR ref to a commit nobody's branch carries. The Run stays `success` and the deploy never happens. Ticket 275 asks for a narrow exception, and this records it.

The exception is narrow by construction: it lives only in `lime deploy`'s pre-merge gate, applies only to `success` Runs, only to paths the roster says the documenter owns, only to conflicts the resolver can merge, and it makes exactly one remote write in place of §2's none.

1. **Deploy-only, success Runs only.** The exception is reachable only through `_cmd_deploy`'s merged-tree gate (`_check_deploy_merged_tree`), which runs only for a Run already `success` and only when `lime deploy` merges it. `lime run`, verify, a batch launch and every other path are unchanged: a conflict there still refuses exactly as §2 says, naming the unmerged files and pushing nothing.

2. **A conflict the roster owns and the resolver can merge.** A conflicted merge is eligible only when every conflicted path matches the `documenter` Role's `writes:` list resolved through the Run's `profile` (`_documenter_writes`), and `docs_merge.resolve` returns merged text for it. A path outside that list, no documenter, an unknown profile, a `writes:` that is not a list, a symlink or non-regular file, non-UTF-8 bytes, or a resolver that returns `None` (a base line both sides changed or removed, duplicate glossary terms, a malformed marker) all keep §2's behaviour: `MergeConflict` names every conflicted path and the gate records `merge_conflict` and pushes nothing. Ownership defaults to none, so an unresolved roster can never widen the exception.

3. **A tested, lease-published merge.** As soon as the resolved merge is staged, before setup or test run, the gate freezes that index (`git write-tree`): the exact tree setup and test then run on, through the same `quality.run_check` §2 uses. Only after setup and test pass is the frozen tree turned into a real merge commit (`git commit-tree`, first parent the PR head, second parent the default tip) — an unreferenced object, so no ref has moved yet. It then `--force-with-lease`s that commit onto the PR branch with the PR head it was tested against as the expected value. The lease is what makes the one ref write safe: if the PR moved under the check the push is refused, records `docs_merge_push_rejected`, and nothing else runs. This lease push is the gate's only remote write, and it is the exception to §2's "every ref untouched" (the Run's own PR branch, and nothing else). From there the gate only reads: it waits, bounded by one two-minute deadline, for the pushed merge to become the PR's `headRefOid`, then reads CI once on that same head. A head that never shows records `docs_merge_head_missing`; a non-green CI records `docs_merge_ci_<ci>`. An empty check rollup on the pushed head counts green only when the PR had no checks before the push, otherwise it counts pending; either way the Run stays `success` and a re-run goes through the unchanged gate.

4. **Exact-head merging.** When the gate resolved and published a merge, `_cmd_deploy` merges the PR with `--match-head-commit` pinned to that tested merge SHA, so `gh` refuses a PR whose head moved after the check instead of merging an untested commit. When no docs conflict was resolved the merge argv is unchanged, exactly as before.

5. **The local Run branch and worktree stay untouched.** The resolution is written and `git add`ed only inside the throwaway worktree §2 already creates; the Run's checkout, the default checkout, the local Run branch and every local ref are untouched — no checkout switch, no merge or rebase into the Run branch, no local commit. The commit-tree object and the lease push are the only new artifacts, and the worktree is removed before the push runs, exactly as §2 requires.

We considered,

- **Keep refusing every conflict and let a person resolve the docs conflict by hand.** Rejected: the resolver already produces the correct merged text, and a hand resolution cannot be tested by the merged-tree gate, so it would land exactly the untested tree the gate exists to prevent.
- **Widen §2 to allow a docs conflict for every path.** Rejected: §2's read-only worktree protects code merges, where a conflict is a real disagreement; the exception is scoped to roster-owned, resolver-mergeable docs paths because those are the only ones a machine can merge correctly.
- **Merge the resolved tree into the Run branch and let the normal deploy carry it.** Rejected: it writes the local Run branch and drags the default tip into it, the exact coupling §2 forbids; the tested tree becomes an object, not a branch.
- **Push the merge without the lease.** Rejected: a force-push without `--force-with-lease` would overwrite another writer's commit on the PR branch, and the tested tree would no longer be the head.
- **Merge the PR at whatever head GitHub reports after the push.** Rejected: between the push and the merge the head can move again, and merging an untested commit is the failure §2 was written to stop.

Trade-offs accepted: `lime deploy` can now move the Run's PR branch, so a docs-only deploy has one ref write where §2 promised none — bounded to the credentials of a lease push that the gate already tested against. A conflicted docs merge now costs a push, a two-minute head wait and a CI read before it can merge, and a refusal after the push leaves a docs merge commit on the PR branch that a re-run re-checks against the unchanged gate. The exception is reachable from `lime deploy` alone; a docs conflict met anywhere else still refuses as §2 says.
