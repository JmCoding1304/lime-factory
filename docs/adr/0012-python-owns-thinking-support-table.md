# Python owns the per-model thinking support table; the client learns it from the server

Every model that routes through pi has a distinct set of supported thinking levels (off, minimal, low, medium, high, xhigh, max), defined by pi's catalog and derived via `supported_thinking()` in Python. Switching an agent's model in the dashboard kept the old thinking level when the new model did not support it — `validateSlot()` only checked membership in the generic `THINKING` enum — so the saved config was silently broken until `lime run` refused it at preflight. We chose to keep Python authoritative (no duplicate table in TypeScript) and have the client learn each model's supported levels from the server via the `thinking_support` field in the `lime profiles get` response, rather than copying the catalog table into the frontend. The trade-off is that client-side validation depends on an async server round-trip and a model absent from the table falls back to the full THINKING enum (last-line defence stays in `lime check`), but any model added to pi's catalog is immediately available to the dashboard without a frontend deployment — the table lives in one place and the cost of the async dependency is paid once on page load, not per interaction.
