# Git is the ticket numbering ledger; reservation refs prevent duplicate numbers

Counting files in `.lime/tickets/` to pick the next ticket number breaks because delete-on-close empties the directory. Numbers 41, 57, 60 and 63 were each issued twice, and two Runs started at the same moment both produced the same number. We rejected the naive fix (stop deleting or rename the directory) because delete-on-close is the tracker's contract — a closed ticket is gone, and keeping it would change the meaning of `ls .lime/tickets/` from "open tickets" to "all tickets ever".

The next free number is `max + 1` over four sources: local `.lime/tickets/NN-*.md`, ticket-subject commits (`git log --all --grep=^ticket: NN-`), origin branch heads (`lime/<workflow>/NN-*`), origin reservation refs (`refs/lime/tickets/NN`), and PR head refs (`gh pr list --state all`). A fresh originless repo returns 1.

A Run must CAS-reserve its number on origin before creating a worktree. The reservation is a lightweight git ref (`refs/lime/tickets/<NN>`) pointing at a Run-unique commit-tree from the default branch tree. `git push origin <commit>:refs/lime/tickets/<NN>` is the atomic compare-and-swap — a second Run racing on the same number gets a push rejection and exits non-zero before touching anything. The same stem re-reserving (a resumed Run) is allowed; a different stem on the same number is refused, naming the conflicting ref and its holder. Reservation refs are never deleted — they are the permanent ledger `next_number` reads.

The trade-off is between simplicity (count files in `.lime/tickets/`, accept duplicates every time delete-on-close hits a gap) and correctness (git as the ledger, requiring git plumbing, a remote origin, and `gh` for PR queries — but guaranteeing monotonicity even during concurrent launches). We accepted the complexity because duplicate ticket numbers cause silent data races in the dashboard, the trace, and deploy logic — a correctness failure that weights more than operational simplicity.
